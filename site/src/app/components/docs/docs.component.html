What is AeroStream?

AeroStream is an open-source, ultra-high-throughput, cloud-native distributed streaming platform engineered around a Dual-Engine Architecture. It combines the distributed consensus stability of Go Raft with the zero-copy performance and mechanical sympathy of a Rust Log Storage Kernel.

lightbulb
Key Drop-In Capability: AeroStream natively implements the Apache Kafka wire protocol on TCP port 9092. Any existing application using kafka-python, Java/Spring Kafka, or librdkafka can point directly to AeroStream without modifying application code or installing sidecars.

Dual-Engine Architectural Rationale

Traditional streaming engines compromise either on developer velocity or low-level mechanical sympathy:

  • JVM Runtimes (e.g. Apache Kafka): Incur heavy memory fragmentation, large object headers (16–24 bytes per reference), non-deterministic Garbage Collection pauses, and high baseline memory and thread overhead.
  • Homogeneous C++ or Rust Brokers: Deliver raw I/O throughput but suffer high development friction when orchestrating dynamic REST APIs, complex Raft consensus FSMs, schema validation engines, and user access control policies.

AeroStream resolves this by decoupling the control plane from the storage data plane:

Subsystem Engine Runtime Core Responsibilities Performance Highlights
Control Plane Go 1.26 (Alpine) HashiCorp Raft Quorum, Schema Registry, RBAC ACLs, Stream Transforms, Connectors Green Tea GC (<1ms pause), SIMD Swiss Tables maps, native Kubernetes cgroup auto-tuning
Data Plane Rust 1.98.1 (Edition 2024) TCP Listeners (Ports 9091/9092), Zero-Copy Segmented Commit Log, Tiered Storage Zero-copy sendfile(2) I/O, microsecond commit latency, lean memory footprint, and lock-free execution

Control Plane (Go 1.26 & Raft Quorum)

The AeroStream Control Plane runs as a dedicated lightweight microservice. It uses the HashiCorp Raft consensus algorithm to achieve linearizable state machine transitions across cluster controllers.

  • Quorum Elections & Health Heartbeats: Brokers send health heartbeats every 2 seconds. In the event of leader loss, Raft elects a new leader in <150 ms.
  • Green Tea GC in Go 1.26: The newly defaulted GC in Go 1.26 slashes garbage collection overhead by 10%–40%, ensuring control plane metadata lookups do not suffer tail latency spikes.
  • Swiss Tables Maps: Go 1.24/1.26 runtime hash maps utilize 16-way SIMD vector probing, accelerating topic partition routing and ACL rule lookups by 30%.

Data Plane Kernel (Rust 1.98.1 & Tokio)

The Storage Broker is built entirely in Rust (compiled with rustc 1.98.1, targeting Edition 2024). It operates directly against Linux kernel APIs for maximum mechanical sympathy:

info
Positioned Writes without Lock Races: AeroStream writes log segments using FileExt::write_all_at. Because each write supplies its absolute byte position directly, multiple worker threads can append to non-overlapping partition segments concurrently without taking file-pointer mutex locks!

Zero-Copy sendfile(2) Pipeline

When clients fetch records, data is read directly from the Linux Page Cache to the network socket using sendfile(2). Data never transitions into userspace buffers, eliminating CPU cache evictions and memory bus bandwidth bottlenecks: 

[ Linux Disk Page Cache ] ──► (Kernel sendfile DMA) ──► [ Network Socket NIC Buffer ]
                               (Zero Userspace Memory Copying!)

Hardware CRC32C Acceleration

AeroStream verifies message batch checksums using hardware instructions (CRC32C on SSE4.2 and ARMv8). This enables 10.9 GB/s checksum throughput, removing CRC computation from the ingestion critical path.

Port 9092 Kafka Wire Protocol Drop-In

AeroStream listens on TCP port 9092, speaking standard Kafka binary frame serialization. It supports standard client batch framing (Magic 2 RecordBatches), metadata discovery, producer idempotence, and consumer groups.

In-Place Base-Offset Patching

Unlike naive compatibility bridges that decompress and re-encode incoming Kafka batches into individual records, AeroStream utilizes in-place base-offset disk patching. Because the Kafka CRC32C covers only bytes 21..len, the broker writes the 8-byte assigned base offset directly at the disk segment offset without modifying or re-allocating the multi-megabyte record payload!

Built-in Schema Registry REST Endpoints

AeroStream embeds a Confluent-compatible Schema Registry directly into the cluster controller (port 9001). It eliminates the need to run separate Schema Registry containers or external database dependencies.

Compatibility Modes

AeroStream enforces industry-standard schema evolution rules:

  • BACKWARD (Default): New schemas can read data written by the previous version (fields may only be deleted or optional fields added).
  • FORWARD: Previous schemas can read data produced by the new schema.
  • FULL: Both backward and forward compatible.
  • NONE: Compatibility checks disabled.

Enterprise Role-Based Access Control (RBAC)

AeroStream implements enterprise zero-trust access control. Users and service accounts are bound to predefined roles with granular permission policies:

  • SUPER_ADMIN: Unrestricted cluster administration, broker draining, and ACL management.
  • OPERATOR: Topic creation, partition rebalancing, and connector deployment.
  • PRODUCER: Write access to authorized topic patterns (e.g. orders-*).
  • CONSUMER: Read access to authorized topic patterns and consumer group coordination.
  • AUDITOR: Read-only inspection of cluster metadata, schemas, and ACL policies.

Cooperative Sticky Rebalance (KIP-848)

Unlike legacy eager rebalancing which revokes all partition assignments across all consumers whenever a pod restarts, AeroStream implements Cooperative Sticky Rebalancing:

  1. Healthy consumers retain their existing assigned partitions uninterrupted.
  2. Only partitions migrating between members are revoked.
  3. Eliminates stop-the-world rebalance storms and lag accumulation in consumer microservices.

Hot vs. Cold Storage Tiers

AeroStream splits event retention into two tiers:

  • Hot Tier (Local NVMe / SSD): Active open segments and recently closed segments are stored on local fast NVMe disks for microsecond tail latency.
  • Cold Tier (Cloud Object Storage): Once a segment rolls (exceeding 128 MB or retention age), a background worker asynchronously offloads both the .log and .idx files to cloud object storage.

Supported Cloud Object Providers

AeroStream supports all major enterprise object storage backends via native async Rust SDKs:

  • AWS S3 & MinIO: High-throughput S3 API with multipart upload support.
  • Google Cloud Storage (GCS): Native GCS bucket integration for Google Cloud deployments.
  • Azure Blob Storage: Azure Block Blob storage for Microsoft Azure enterprises.

info
Apache Kafka was CPU-bound; AeroStream was not. Kafka sat at or near the 2-CPU cap for 84% of the run and never dropped below 100%. AeroStream delivered about 32% more messages while averaging about a third less CPU, so it did roughly twice the work per unit of CPU. Its CPU use also came in repeating bursts: peaks near 200% followed by several intervals at 55-80%. That pattern means the broker was not limited by CPU during the dips. Its cause is still under investigation.

Temperatures were read from the hardware sensors at the start of each run. They were not logged continuously during the runs, so mid-run thermal throttling cannot be ruled out.

Caveats

warning
Read these numbers as indicative, not definitive.
  • Each broker was measured once. On this machine, run-to-run variation of about 20% is common.
  • The runs were about 30 minutes apart and were not interleaved.
  • This is a shared laptop, not a dedicated benchmark server, and other applications were running.
  • Apache Kafka ran with stock settings and no tuning.
  • Only the Kafka wire protocol at 1 KB messages was measured. Other message sizes and the native protocol are not covered here.
  • Temperatures were sampled at run start only.
  • Redpanda results are not included yet.
